## 2. "忠实镜像窄链"的**结构推导**（本片的核心设计；每一条都可核）

### 2.1 窄链的形态（对照物）

窄链 = `L_MAX` 片 `Conv3x3Slice`（各带 `WeightStore`）+ `L_MAX+1` 个 `FusionBuf`；切片 `i` 读
`bufs(i)`、写 `bufs(i+1)`（行锁步：`wrote-read ∈ {0,1}`，3 行环窗恰好够）；末片写 `outMemT`→DDR；
中间张量**结构性零 DDR**（写口只被切片输出/pad 注入驱动，见 `UnitExec.scala` 文件头 A-1a 一节）。

### 2.2 宽链的逐片引擎（镜像的落点）

宽层的**一个成员** `k`（`C_in=CIN_k, C_out=COUT_k`，`nCi_k=ceil(C_in/8)`、`nCo_k=ceil(C_out/8)`；
dw ⇒ 对角趟 `nCo_k`）在硬件里 = `nCi_k×nCo_k` 趟（每趟 = 8×8 切片 + 一个 576 B 趟瓦片）。镜像：

- **每片一个"趟引擎"** = 8×8 切片（自有 `WeightStore`）+ **每片一个逐行部分和缓冲** + **每片一个
  常驻权重段 RAM**（`Σ_k ceil32(N_k)`，就是 B3 的那一项）+ **每片一个趟瓦片装载器**（段 RAM →
  WeightStore，576 B/趟，1 B/拍）。
- **行锁步（跨片）**：成员 `k` 产出**输出行 `q`** 的完整像素字（`COUT_k` 个通道）后拉手；
  成员 `k+1` 从**环**里取该行（它的 `ci` 块 = 上游的 `co` 块，`FusionBuf` 环的"宽字"= 一像素
  `NCOB×8 B`）。环 = 3 行 × `WINDOW_k` 像素 × 8 co-block 字（≈6.5 KB/边界）。
- **趟序（每行）**：对输出行 `q`，扫 `(cob 外, cib 内)`（dw 为对角）——每趟：载瓦片(576 拍) →
  `prime` → 喂**本片窗口的 3 行**（`prime` 会清 `LineBuffer` 历史 ⇒ 每趟必须重喂 3 行 = 延迟出料
  的"多喂 2 行"口径，与 T-S2R tile 的 `tNRow = th+2` 同式）→ 末 `cib` 趟的出料（requant 一次）
  写环。**部分和在逐行缓冲里跨 `cib` 累加**（同一像素 + `cob*ROWMAX + pix` 槽；初值 0 = 上电态）。
- **嵌套窗口**（承重几何）：L 片 3×3 串联 ⇒ 输入窗比输出 tile 每片各扩 1 列/行：末片输出
  `T×T`，片 `k` 的窗 = `T + 2(L-1-k)`；片 0 的输入窗 = `T + 2L ≤ WIDTH=34` ⇒ **T ≤ 34-2L**
  （L=2→30 / L=4→26 / L=6→22 / L=8→18）。tile 网格按末片输出切（`tNtx/tNty` 现有式），
  片级窗口是运行期量。
- **喂料**：片 0 = 现有 `wx` 平面 gather（按嵌套窗口重算 halo，机器不变、参数变成逐片）；
  片 `k>0` 的 `x` 列 = 环 `k` 的像素字第 `cib` 个 8 通道块（**零 DDR**）。
- **收尾**：末片输出仍是 `[co][y][x]` 逐字节拼拍 + 掩码行 burst（既有 `wt*` 机器原样复用）。

### 2.3 数值等价（为什么能逐字节）

每个像素的累加集合/顺序无关（整数加法结合律；部分和 32 bit 由 §3.7 的界 `9,363,456 < 2^24` 担保），
requant 仍在**末 `cib` 趟**、每像素每 `cob` 一次；"一行一趟扫"与"整层一趟扫"的**逐字节结果相同**
（趟的空间范围变了，像素的加数集合没变）⇒ 可对 `chain_wide_ref.py`（参考 #2）逐字节。

### 2.4 与既有 `MultiPassUnit` 的关系（**明写**）

**不是扩展、是第二个引擎**：`MultiPassUnit` 的冻结形态是"趟 = 整个 tile"（`(H+1)×W` 列喂一遍 +
tile 深度的 `PartialSumBuf`），它**无法**表达"每行一趟"的跨片行锁步（行级上下文 = 切片内
`LineBuffer` 状态，无法在片间共享/保存）。⇒ 镜像必须**每个链片一套引擎**（或与窄链共用片阵列，
见 §5 的合体变体）。

## 4. 镜像的资源账（**这是 BLOCKED 的测量**）

### W1 —— LUT：**每片一套引擎放不进板级预算**（实测）

- 镜像需要 `L_MAX=8` 片**并发**（真表 `run[4..11]` 就是 L=8），每片 = 8×8 切片 + 行缓冲 +
  `WeightStore` ⇒ **+8 × 6,202 ≈ +49,616 LUT**。
- 余量 = **35,692** ⇒ **超 ≈13,924 LUT**（≈ 器件的 8.7%）。
- ⇒ 该档**不能以"新增片引擎"落地**（`dev_map` 会红）。这不是估：`6,202 LUT/片`与 `35,692` 都是实测数。

### W2 —— 唯一在预算内的变体 = **与窄链共用 8 片切片阵列**（合体引擎，需裁决）

- 宽链跑的时候窄链是**全闲**的（`isWide` 的运行里 `cst/cons` 一律不进 `PRES`）；窄链的
  `slices(0..7)` 恰好 = `L_MAX=8` 个链片 ⇒ **0 新切片**，ΔLUT = 仲裁器 + 编排（估 +10~25k，在余量内）。
- 代价 = 把 `slices(i)` 的**全部接口面**变成"窄/宽二选一"（每片 8 组、共 8 片），**逐字节冻结面清单**：

| # | 面 | 现状（file:line，UnitExec.scala） |
|:--|:--|:--|
| 1 | `we/waddr/wdin`（信箱/DMA → `WeightStore`） | 1094-1099 |
| 2 | `requant_m/zero_y/pad_val/stride/rowW/ps_in/bias` | 1100-1112（`mR/zyR/zpadR` 是**链首一个值**，引擎需要逐片值） |
| 3 | `x/x_valid`（消费子 FSM 喂列） | 2467-2524（`sl.io.x := rdY`；`PRES` 里 `x_valid`） |
| 4 | `prime` | 2705-2706（`primeR(i)`） |
| 5 | `y/y_valid` 的消费者 | 1326/1338（`outMem`）、2527-2554（`ocol`/中间缓冲写）、2575-2576（`pixIdx(T)`）、2452-2456 |
| 6 | `midWrEn` 字面行（闸门外科锚） | 2464（`run_fuse_head_ab.sh` 按逐字抓） |
| 7 | 参数读回（`mzRam`→`mR/zpadR/zyR`；`biasMem`→`biasReg`） | 761-870/917-923（现为**单份**；引擎需要逐片 8 份） |

- ⇒ 合体变体**技术上可行**，但它（a）是"**把窄/宽两个引擎并到一个片阵列上**"——pin 死的口径
  （"忠实镜像、不发明平行设计"）没有授权这一类**结构性合并**；（b）把上表 7 组冻结面全部打开，
  窄链的判据面（`run_chain_ab` / `run_chaingeom_ab` / `run_tiling2d_rtl` / `run_wgtblob_tiled`
  共用 `gen/UnitExec_tiled.v`）是本项目的**红区**。⇒ **停在这里，交用户裁决**。

### W3 —— DRM：**贴边**（按跑形 sizing 才过）

| 项 | 公式 | 字节 |
|:--|:--|:--|
| 逐片常驻权重段（**一个共享池**，逐跑 sizing） | 真表最坏 `run[23..28]` Σceil32 = **112,320**；闸门 `c64_L4` = **147,456**；naive `8×36,864` = **294,912** | 112–295 KB |
| 逐片逐行部分和 | `8 × (8×34 字 × 32 B)` = 8×8,704 | 69,632 B |
| 跨片环（宽字 = 一像素） | `7 × (3 行 × 34 像素 × 8 字 × 8 B)` | 45,696 B |
| **合计** | | **228–410 KB vs 余量 ≈376 KB** |

⇒ 逐跑 sizing 的共享池（112–147 KB 档）**过**（≈262 KB，占余量 ~70%）；naive 逐片满配（295 KB 档）
**不过**（410 KB > 376 KB）。**R1 的"零新增宽存储"纪律在镜像下必须松动**（明写）。

### W4 —— 拍数：闸门内**贴边**、真帧 fps 是新增代价（不是闸门墙）

- 每个 `(行,趟)`：载权 576 拍（`WeightStore` 写口冻结 8 bit）+ 喂 3 行 × 窗宽列（列收率 1/11）。
- 闸门作业（`+TMT=2000000`）：`c64_L4`（64→64，20 行，64 趟/行，窗≈28 列）⇒ 每片 ≈ 20×64×1,500
  ≈ **1.9M 拍** + 流水填充（3×93k）⇒ **≈2.1–2.2M，越 `TMT` 边界** ⇒ finisher 需把闸门的 `+TMT`
  抬到 ~3M（**夹具旋钮**，非设计墙；TB 全局看门狗 8M 不动）。
- 真帧（诚实记账）：`run[4..11]` 160×160、L=8、81 tile ⇒ ≈**1×10^8 拍/run ≈ 1 s**（今日单单元
  宽路 ≈0.3 s 的同形类推）⇒ 帧级 fps 再降 ~3×。spec 早已把 fps 单列为开口项（S2b-ii），此处只是
  **把数字钉下来**，不构成本片的 BLOCKED 理由。

## 5. 判词与裁决点

**BLOCKED（本片）—— 三条裁决线，任一成立即可解锁**：

1. **合体变体获授权**（推荐）：宽链与窄链共用 `slices(0..7)` 片阵列（宽跑时窄闲、窄跑时宽闲的结构
   性互斥），ΔLUT = 仲裁器 + 编排（余量内）；DRM 按 §4-W3 的共享池 sizing。需要用户明确授权
   "打开 §4-W2 的 7 组冻结面"（窄链判据面重新对账的一次性成本）。
2. **只求闸门绿（L≤4）**：新增 4 片引擎（+24.8k < 35.7k 余量）⇒ 闸门 4 个作业可绿，但真表
   `run[4..11]`（L=8）与 `run[23..28]`（L=6）仍无路 ⇒ **不满足任务的目标**（真帧跑不完），需表侧拆链
   （`desc_table.py`，另一个 slice）配合才完整。
3. **撤回镜像、回到 spec §3.6 的"逐片串行 + 嵌套窗口"**（本任务显式排除的档）。

本片按任务约定**停在已提交的检查点**（commit 见 `git log`；`gen/` 未动、红签名未变）。
