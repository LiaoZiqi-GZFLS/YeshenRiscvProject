# P4：板级 DDR 读仲裁**多未完成** —— 解锁 DDR3Bridge 的 4 笔在飞

状态：**RTL 改动 + 单元闸门全绿（2026-10-21）；待 PnR/上板 A/B**。
改动只在板级 `board/cam/ddr_arbiter_2to1.v`（读通道）+ 仿真模型 `sim/video/ddr_model.v`（加 ARDEPTH 参数，
默认 1 = 旧行为）；**NPU / glue / DDR3Bridge 的网表零改动**。

## 0. 一句话

所有 NPU 取数都被**板级 2:1 仲裁器**压成单笔 outstanding —— 桥内 `DEPTH=4`、NPU 的 `rqDepth=8` 在这里
全部失效。本轮把读通道改成「桥 ≤4 笔、视频 1 笔在飞 + rid 分流 + 轮转」，其余语义逐条不动。

## 1. 证据链（为什么锁定这一级）

| # | 观测 | 指向 |
|---|---|---|
| 1 | P3（NPU `rqDepth` 4→8）上板 **+0.008%**（`2,167,938,030` vs `2,167,760,940`，12/12 CRC） | 瓶颈在 NPU 队列**下游** |
| 2 | B3b（8 平面一次进队）−17.1%：8 次逐平面往返 → 1 批；再加深队列无效 | 每次往返单价很高、并发度被卡 |
| 3 | B3a 省 2.368 MB ⇒ −110 ms = **46 ms/MB**（≈22 MB/s 的取数边际价） | 取数速率 ~0.4 B/拍（54 MHz） |
| 4 | B2 map 反解：冷 32B 突发 **2.08 µs/笔**；B3b 后等效 ~1.4 µs/笔 | 每笔固定开价 ~0.96–1.4 µs |
| 5 | 板级 `ddr_arbiter_2to1.v` 旧读通道：`R_IDLE/R_WAIT`，**只有上一笔 `m_rlast` 回来才进下一笔 AR**；`b_arready = (R_WAIT && rsel==0 && m_arready)` | **结构性单笔**：桥的 DEPTH=4 在此归 1 |
| 6 | 视频同口径：`VIDEO.STATUS` 10 s 走 168 帧（16.8 fps）；`DBG` 读等待在视频侧也在涨 | 视频与 NPU 共用同一单笔通道 |
| 7 | 桥自己的 B2B 闸门（DMA-P0）：`DEPTH=4` 下读 8×32B = 45 拍（569 MB/s） | 桥/CDC **有能力**多笔；卡点不在桥 |

⇒ 结论：**把仲裁器读通道放开到与桥的 DEPTH 一致（4）**。这是一条板级结构改动，不动任何地址/数据语义。

## 2. 契约（`ddr_arbiter_2to1`，新增参数 `BN=4, VN=1`）

- **AR 递交**：握手寄存器 `ar_hold` 一次装一笔，等 IP `m_arready`；上一笔被 IP 收下即释放，
  下一拍可接新 AR（吞吐 1 笔/2 拍；IP 的 `m_arready` 天然反压）。
- **在飞计数**：`b_out`（桥）/`v_out`（视频）= IP 已收 AR − 已回 `rlast`（按 `m_rid` 记名）。
  `b_out < BN` / `v_out < VN` 才接新 AR ⇒ **未完成数结构性 ≤ BN/VN**。
- **公平**：两方都有请求时轮转（`rr`）；视频 `VN=1` ⇒ 视频未完成语义与旧版**完全相同**，
  且视频 AR 最多压桥一个发放槽（结构上不会被桥饿死）。
- **R 分流不变**：`m_rready = (m_rid==1) ? v_rready : b_rready`；`b_rvalid/v_rvalid` 按 rid 门控；
  同一属主的 AR 按序发出、IP 按序回 R ⇒ 每个口看到的 R 与自己的 AR 同序。
- **计数纪律**：`AR 收下` 与 `rlast 回来` 同拍发生时净变化为 0（同一条表达式），不跳笔、不绕圈。

## 4. 影响面与回退

- **网表**：NPU/glue/bridge 的 `.v` 与 md5 **零变化**；只重跑 PnR（板级 Verilog 变了）。
- **资源**：仲裁器新增 ~2 个 3 bit 计数 + 握手寄存器 + 少量 mux（<100 LUT/FF）。
- **视频**：`VN=1` ⇒ 视频未完成语义不变；U2 逐像素全绿。若屏上出现成块错位/闪动 ⇒ 立即回退。
- **IP 能力**：若真实 DDR3 IP 的 AR 队列放不下 4 笔，`m_arready` 会自然反压 ⇒ 行为退化回单笔（不会错），
  只是没有收益 —— 由板级 A/B 裁决。
- **回退**：`git revert` 本文件两处（仲裁器 + 模型）即可；P3 的 `rqDepth=8` 若 P4 无收益也一起回退。

   12/12 CRC 必须全对。

4. 顺带取 `VIDEO.STATUS/DBG` 前后各一次（帧序号、视频读等待），确认视频没被饿死。

**预测（不是判据）**：若 IP 真能吃 4 笔，dw/fill 的取数单价 ~1.4 µs → ~0.4–0.5 µs/32B，
fill 从 ~41 拍/px 降到 ~15–20 拍/px，整帧 **2.17 s → 1.3–1.6 s（0.63–0.77 fps）**；
若 IP 只吃 1–2 笔，收益按比例缩水。以板级读数为准。

## 6. 上板 A/B（2026-10-22，tag `video1p5`，sbit `fc08f0d3…`）

- 烧写 done bit=1；相机/屏画面**恢复正常**（用户目视："画面可以了"）。
  ⇒ 旧仲裁器读 FSM 的 `arready = R_WAIT && rsel==x && m_arready` 在 `m_arvalid` 已落时仍回
  ready，会**静默吞掉**主方一笔 AR（视频侧被吞 ⇒ rd_ctrl 等不到 rlast ⇒ 帧存读指针漂 ⇒ 花屏/闪烁）；
  P4 的握手寄存器式读通道结构上消除该路径。
- `y1run --frames 2`：**RUN 2,074,548,660 / 2,074,386,530 ns**（稳态 2.0744 s），
  vs 基线 2,167,760,940 ⇒ **−93.2 ms（−4.3%）**，12/12 CRC 全对。
  ⇒ 多未完成读**有效但幅度小**：DDR 读路径的真实瓶颈不在仲裁器并发度。
- `y1cam --once`：NPU_MS **2074**（P3 带 2169）、`BOARD_INPUT_CRC=977d8787`。
- 逐单元表（`y1/reports/unit_trace_p4p5.txt`）按类：
  conv1x1 951.8→909.3、dw 691.5→653.2、conv3x3 237.7→232.1、maxpool 177.0→172.5、add 73.3→71.3 ms。
  dw 40.3→38.1 拍/px（仍远离 11 拍地板）。
  ⇒ 下一步嫌疑：**NpuMemCdc 的 R 通道按 8 B/拍做四相跨域**（4 lanes），
  与桥的 rCdc 串联后有效带宽 ≈ 0.4–0.5 B/拍（~22–24 MB/s），与实测吻合；
  杠杆 = 加 lanes 或把 R 数据换成真异步 FIFO/加宽载荷（待量化验证）。
