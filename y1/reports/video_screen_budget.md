## 2. 读路（`rd_buf`）：实测可容忍一整个显示行（25.2 µs）

新闸门 `y1/tools/run_rdbuf_lat_ab.sh`：真 `rd_buf` + 行为等价 `rd_fram_buf`
（`y1/tools/rdbuf_bram_model.v`）+ 真实 1024×600@51.923 MHz 时序（H_TOTAL 1344 /
V_TOTAL 635，与 `video_passthrough.v` 一致）。DDR 模型在请求后 `LAT` 个 ddr_clk
（125 MHz）给第一拍，共 64 拍；每 16 bit 字带"请求序号"，因此屏上取到的字能直接
指出**它其实显示的是哪一行的数据**。

| `LAT`（ddr_clk） | 等效时间 | MISMATCH / 612000 |
|---|---|---|
| 0 | 0 | 0 |
| 2000 | 16.0 µs | 0 |
| 3000 | 24.0 µs | 0 |
| 3150 | 25.2 µs | 0 |
| 3250 | 26.0 µs | **609964**（> 一显示行，红） |

结构解释：`wr_trig <= wr_rst || (~wr_en_3d && wr_en_2d && ...)` 是 `rd_en` 的
**上升沿**（`wr_en_3d` 比 `wr_en_2d` 旧 ⇒ 旧 0 新 1），即**每个显示行开始时就发
下一行的 DDR 读**；`rd_fram_buf` 实为 8 行环形（写 512×256 = 读 4096×32 = 8 行），
读者读第 k 槽、写者填第 k+1 槽，互不重叠。
⇒ **读路预算 = 一个显示行 25.89 µs**，等价"2 KB/行 ⇒ ≥79 MB/s 且 AR 首拍延迟 < 25 µs"。

结论：读路不是脆弱点；只有 DDR 对视频读**整行**低于 79 MB/s 才会花，那已是接近
饿死的程度（`vid_stall` 会同步暴涨）。

> 注意：本闸门的负对照（LAT=3250）在模型里表现为"上一笔未完成又发新请求 ⇒ 丢请求"。
> 真硬件里该请求会排在仲裁器里、晚到的数据落进下一槽 ⇒ 同样是错行。两种情形都判红。

### 2.1 与仲裁器策略对账：NPU 争用最多吃掉 ~2 µs，预算有 ~13× 余量

`board/cam/ddr_arbiter_2to1.v` 的读通道（`BN=4`、`VN=1`、两方都有请求时轮转）：

- 视频侧**只有 1 笔在飞**（`v_out < VN=1`）；桥侧最多 4 笔。
- 视频 AR 最坏排在**已被 IP 收下的 ≤4 笔桥 burst** 后面：4 × ≤512 B ≈ 2 KB
  ⇒ 在 ~2 GB/s 量级上 ≈ **1 µs**；再加视频自己 2 KB（64 拍）≈ 1 µs ⇒ **合计 ~2 µs**。
- 预算 25.9 µs ⇒ **余量约 13×**。NPU 提到 60 MHz 只把请求速率抬高 11%，不改变"在飞笔数上限"
  这个决定性因素。

⇒ **若集成版（NPU/CPU 同时跑）出现花，读路争用不是合理机制**；`video_health.py` 的
`vid_stall` 增量会是几拍~几十拍（正常），而不是上千。那时应先查
（a）帧存写路（§3 的"某行写排队 > 一行 ⇒ 整槽被覆盖"）、（b）相机侧（接线/寄存器/曝光）。

## 3. 写路（`wr_buf`/`fram_buf`）：无背压输入，靠环形自身跟得上

- `rd_bac` 端口在 `wr_buf.v` 里**声明但从未使用**（`grep -n rd_bac` 只有第 41 行）。
- 帧存同样是 8 行环（写 `wr_addr` 12 bit = 4096 字 = 8×512，读 `rd_addr` 9 bit = 512 拍 = 8×64）。
- 整行齐（`x_cnt==H_NUM`）才 `rd_pulse`→发一笔 DDR 写；短行**整行丢弃**并回滚 `wr_addr`
  （这是更早修的"短行导致逐行水平错位 + 通道偏色"）。
- 需要的能力：摄像头每行 2 KB 必须在该行周期内被 DDR 写走（≈60 MB/s @ 34 µs/行）。

⇒ 写路没有"随压力增大而优雅降级"的机制：只要某一行写排队超过一行周期，该槽就被
下一行覆盖 ⇒ **整行错位/花**。这与 2026-10-21 抓到的"帧存里本身就是花的、G 干净
而 R/B 高频杂色"形态一致。

## 4. 判定所需的板级对照（窗口开放时一次跑完）

三种工况各抓一份"帧存镜像 + 屏上截图 + `vid_stall`/帧序号"：

1. **CPU+NPU 空闲**（只跑 `y1cam` 直通）——与 cam2lcd 对照；
2. **NPU 满载**（`y1ctl run /root/y1/y1run --frames 3`）；
3. **CPU 满载**（板内 `yes >/dev/null &` 多份）。

判据：
- 若 1 正常、2/3 花 ⇒ 争用确认；再按 §2/§3 的带宽账定位是读饿死还是写覆盖
  （读饿死伴随 `vid_stall` 暴涨；写覆盖时 `vid_stall` 低但帧存镜像已坏）。
- 若 1 也花 ⇒ **与 NPU 无关**，回到相机侧（接线必须直插、`0x3503`、采相位、彩条
  测试图案 0x503D=0x80）逐项二分。
