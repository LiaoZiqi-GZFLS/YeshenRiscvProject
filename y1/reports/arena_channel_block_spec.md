# 通道分块 arena 布局（CB-layout）：把 gather 的请求数降一个量级

状态：**spec（未动代码）**。上游证据：`unit_trace.md §6`、`bypass_sg_spec.md §10–§11`、
`ddr_bridge_read_perf.md`。

## 1. 为什么只剩这条路

`b1sg`（旁路 SG 批式，1,262.4 ms / 0.792 fps）之后的实测账：

| 项 | 数值 | 含义 |
|---|---|---|
| conv1x1 | 585 ms（46%） | fill `b`=211 ns/px·ci（35%）+ 每趟成本 |
| depthwise | 355 ms（28%） | **92% 是 fill** |
| conv3x3（`Conv_0` 为主） | 154 ms（12%） | 窄路整行 burst，已是最粗粒度 |
| 旁路四算子 | ~164 ms（13%） | 本轮已从 264 ms 降下来 |

三条已证否的替代：
- **在飞加倍**（`rqDepth 4→8` / 桥 RDEPTH=8）：板级 **−0.002%**，下游 DDR IP 钉死 4 笔；
- **更大突发**（128 B 组）：过读 65% ⇒ 板级 **−12%**；
- **提频**：PnR 60→66.67 MHz **不收敛**（−2.49 ns），且随钟部分只占 35%。

⇒ 宽路的 fill = `请求数 × LAT/4`，字节数已经 nominal×1.13（b1 闸门实测）。**请求数**是唯一还没动过的乘数。
现状：一个请求 = **一个平面**的 32 B。若把同一 tile 窗口内 **8 个通道**的字节在 DDR 上放成连续，
一个请求就能服务 8 个通道 ⇒ 请求数 ÷8（字节数不变）。

## 2. 布局定义（只改"激活张量"的 arena 摆放，不改权重/描述符）

现布局（planar，`B3` 定的）：平面 `(ci)` 连续，`addr = base + ci·H·W + iy·W + ix`。

CB 布局（**按 32×32 tile 分块、块内 8 通道交织**）：

```
addr(tile_y, tile_x, cblock, ci_in_blk, iy_in_tile, ix_in_tile)
  = base + tile_index·(8 · 32 · 32) + iy_in_tile·(8·32) + ix_in_tile·8 + ci_in_blk
```

- `tile_index` 按 (tile_y, tile_x, cblock) 线性编号；块内 32×32 像素、8 通道**交织**（每像素 8 B）。
- 一个 tile 行（32 像素 × 8 通道 = 256 B）在 DDR 上连续；34 列窗口 = 2–3 个 32 B band 仍在同一页内。
- 尾部 tile（不足 32）按 32 补齐（pad 0），**读取端不读 pad**（`tTxEnd/tTyEnd` 已有）。

## 3. RTL 侧改动（`UnitExec` 宽路 gather）

1. `wxPl0/wxRowBas/wxGAbs` 从"平面步进 `tInPixW`"改成"块内交织步进"：
   `wxGAbs = tileBase + (iy_in_tile·32 + ix_in_tile)·8 + ci_in_blk`。
2. **SG 批的项数从 8（每平面一项 32 B）变成 1–3（每 tile 行 256 B 拆 2×128 B）**；
   `sg_beatsM1` 由 3 变 15；`xwBuf` 落点保持 `(pl, 4 字)` 布局不变（RD 流按 8 B:8 通道落列）。
3. `tileBuf`（B1）与 `wxCol` 的取列逻辑**不变**（仍是"每列 8 字节"），只是数据来自更少的请求。
4. 关闭 `tInPixW` 相关地址乘加（顺带把 npu_clk 头号路径的一级乘法拿掉）。

## 5. 迁移与风险

- **风险 1（最大）**：布局一改，**所有黄金/16 道闸门的期望值都失效**；必须"参照先改、闸门重锚"，
  不能靠改锚点掩盖差异（本仓有"参考与 DUT 共用错约定 ⇒ 全绿"的前科）。
- **风险 2**：`y1_common`（CPU 侧驱动）写输入、读输出都按 planar；CB 化后 **head 层输入**要由
  CPU 按 CB 摆好（或在 NPU 侧加一个"planar→CB"的转换趟）。
- **风险 3**：尾部 tile 的 pad 会让 arena 涨 ~3–6%（28 MB carve 现余量需复核）。
- **分两步走**（建议）：
  - **CB-1（只读不写）**：只把**输入**激活改成 CB，输出仍 planar。改动集中在一个 gather + 一个
    converter 函数，闸门只需换黄金的"输入侧"，输出侧不动 ⇒ 风险可控，预期 −8~−12%。
  - **CB-2（读写都 CB）**：再接输出侧，进一步省 tile WR 的请求。

## 6. 装置判决（2026-10-25）：**CB 不值得做**，且这条数据钉住了整个 NPU 的读墙

用本仓现成的桥吞吐装置（`rtl_test/DdrBridgeReadPerfTb.v`，本次给它加了 `+QD=` 队列深度旋钮，
默认 8 = 历史口径不受影响），在 **LAT=640 ddr 拍**（= 板级实测的冷读延迟）下扫：

| ALEN | 每笔字节 | K（AXI 在飞） | QD（DDR 命令队列） | **MB/s** |
|---:|---:|---:|---:|---:|
| 3 | 32 B | 4 | 8 | **24.2** |
| 3 | 32 B | 4 | 4 | **24.2** |
| 15 | 128 B | 4 | 8 | **24.9** |
| 15 | 128 B | 4 | 4 | **24.9** |
| 15 | 128 B | 3 | 4 | **24.9** |

读数：
1. **128 B 突发只比 32 B 快 3%**（不是早期 49.7 的 2×——那是 RDEPTH=8 档，板上已证不可达，−0.002%）。
   ⇒ **CB 的"请求数 ÷2.67"换不来带宽**：每个 AXI 槽的字节吞吐是固定的，变大请求只是让一个槽占更久。
2. **QD 8→4 完全无差** ⇒ 约束在 AXI 侧 K=4（桥/仲裁/IP 在飞上限），不在 DDR 命令队列。
3. ⇒ 读通道的有效带宽 ≈ **24.2 MB/s**，与 `ddr_bridge_read_perf.md` 的板级反推值一致。

**由 3 推到的整帧地板**：本帧 conv/dw 的 gather 字节 = **22.57 MB**（§3 的校准账本）+ 旁路读 ~1.6 MB
⇒ 光读就 **≈ 1.0 s**。当前 1.262 s 距此地板仅 ~25%（其余是能与之重叠的算）。

> ★ **2026-10-25 更正**：22.57 MB 是按"每个 tile 读满 34 列"的模型算的，**没有按 RTL 的
> tile 边界裁剪**（`ox1/oy1 = min(..., Wo/Ho)`，闸门 `gexp()` 同口径）。按裁剪口径重算
> 整帧 = **17.42 MB（nominal×1.143）**，读地板 ≈ **720–790 ms**；板上逐单元反证见
> `gather_overlap_spec.md §2`（dw 逐个贴 99–100%，conv1x1 只有 37–85%）。
> ⇒ "1 FPS == 读地板" 的结论作废：地板不是 1 s，1 FPS 可由**填数/算重叠**拿到（同文 §3–§5）。
⇒ **1 FPS 恰好等于"读带宽地板 + 零串行"**，在这个读通道上已无可腾挪的 NPU 侧空间；
   真要再快，只能抬 AXI 在飞（DDR IP/桥侧，非 NPU RTL）或减少**字节**（halo 已只多 13%）。

**处置**：CB-1/CB-2 **不做**（改转换器 + 16 道黄金，换 ≤3%）。本条与 §11 一起作为"为什么停在这里"的证据。
