# 自研小型 YuNet 加速器（Y1）小 spec

- 日期：2026-10-08
- 工程：VexiiYeshenLinux（VexiiRiscv **RV32** Linux SoC，盘古676 200K MINI / Pango **PG2L200H-6IFBB676**）
- 状态：**待用户审阅**
- 与 M0 的关系：M0 判第三方加速器**默认配置装不下**（`ai_npu_exp/reports/resource_m0.md`）。本 spec 走另一条路 —— 自研一个小到能装下的、**原生支持分组/深度卷积**的 YuNet 专用加速器。

---

## 0. 为什么这条路成立（依据）

`ai_npu_exp/reports/yunet_compute_profile.txt`（由 YuNet ONNX 实测算出）：

| 量 | 值 |
|---|---|
| 单帧算力 | **344,224,000 MAC**（= 688.4 M-FLOP） |
| 权重 | **51,520 个元素 ≈ 50.3 KB**（int8） |
| 层间激活流量 | **31,942,400 B ≈ 30.5 MB/帧**（int8，Conv 输入+输出合计） |
| 最大中间张量 | 1.56 MB（1×64×160×160） |
| MAC 构成 | dense 81.5% / **depthwise 18.5%**（group 直方图 `{1:33, 4:3, 10:3, 16:2, 32:2, 64:10}`） |

三条推论：
1. 权重只有 50 KB ⇒ **整网可常驻片上**（≈11 个 DRM / 415），无权重带宽问题、无需每层重载。
2. 面积几乎只由 **MAC 阵列规模**一个旋钮决定；而 344 M-MAC 算力很小。
3. 第三方加速器的 1152-MAC 阵列是为 YOLOv5s 类（≈7 GMAC）配的 —— 用在 YuNet 上浪费约 20 倍。它的 NO-GO **不是 YuNet 的结论**。

相机侧已去风险：兄弟工程 `cam2lcd_200mini` 已把 **OV5640(J10) → cmos_8_16bit → fram_buf → DDR_200H → LCD** 整链**上板跑通**（11 个调试点全闭环），实测相机 **1280×720 RGB565 @ 15.7 fps**。

## 1. 冻结参数表（本 spec 的硬约束）

| 项 | 冻结值 | 依据 |
|---|---|---|
| 输入 | **640×640**，RGB888（自 1280×720 letterbox，前处理做 RGB565→888） | 工作点决策；YuNet 原生 640² |
| 目标帧率 | **≥ 10 fps**（预算上限 18.6 fps） | 跟上相机 15.7 fps 的 ~2/3 |
| 主时钟 | **`soc_clk` = 100.000 MHz** | `constraints/yeshen_mini.fdc`：`cpu_clk` period 10.000 ns；板级 PLL `pll_100m_125m.v` CLKOUT0 |
| DDR 侧时钟 | **`core_clk` = 125 MHz** | 同上 fdc（DDR IP 自己的 core_clk 输出） |
| MAC 阵列 | **8（C_in）× 8（C_out）= 64 个 int8×int8→int32** | 344 M-MAC ÷ 64 = 5.38 M cycle = 53.8 ms @100 MHz ⇒ 18.6 fps |
| 分组卷积 | **原生支持** `group ∈ {1, C_in}`；depthwise 为特例（一次算 1 个输入通道） | YuNet 20/53 层是分组卷积，第三方设计缺此项 |
| 卷积核 | 3×3 与 1×1（YuNet 只用这两种） | ONNX 实测 `k=[3,3]` / `k=[1,1]` |
| 步长 / 填充 | stride ∈ {1,2}；padding = 1（3×3） | ONNX 实测 |
| 权重存储 | int8，**整网常驻片上**（≤ 50.3 KB） | 画像 |
| 激活存储 | int8；**必须做层融合**（见 §2.1），被略掉的中间张量不落 DDR，其余落 DDR；片上放行缓冲 + 融合缓冲 | 由 C0 流量分析定：见 §2.1 |
| 行缓冲 | 每层 on-chip **N 行/通道**，**1.0 先定 N = 3** | 待 Y2 面积/利用率标定（见 R2） |
| 激活函数 | **ReLU** | YuNet 实测激活只有 `Relu 15` 与 `Sigmoid 6`（Sigmoid 在头侧，见 §5 R5） |
| 量化 | **int8**；权重与激活都按**每层** `scale` / `zero-point` 量化（由 Y3 的转换器算出，硬件只消费参数），累加用 int32 | 沿用 M0 探明的 bias/scale/shift 范式 |
| 主机接口 | **AxiLite4 寄存器从口**（32 bit 地址、32 bit 数据） | 与 M0 加速器同构，复用已验证连接方式 |
| 数据面 | **AXI4 主口**接本仓现有互连（经 `DDR3Bridge`） | `board/yeshen_mini_soc.v` 已有三条 AXI 主口 |
| 输出 | 12 个头张量（3 尺度 × cls/obj/bbox/kps）写回 DDR | ONNX 实测 |

## 2. 预算表（验收时按此比对；数字均为**推算**，须由 Y2 实测替换）

### 2.1 DDR 带宽：约束与已定的调度（2026-10-08 由 C0 定案）

进 DDR 的通路已静态钉死：`DDR3Bridge` = **275.9 MB/s**（6 拍@100 MHz + 7 拍@125 MHz = 116 ns / 32 B；`y1/partA/ddr_path_ceiling.md`）。

| 目标档 | 允许流量 | 调度 | 实测（模型）流量 | 隐含帧率 | 余量 |
|---|---|---|---|---|---|
| 10 fps | ≤27.59 MB/帧 | `fuse_native`（只融合 `1×1→3×3`，26 对） | 17.80 MB/帧 | 15.50 fps | **+55%** |
| 15 fps | ≤18.39 MB/帧 | **`fuse_both`（两个方向都融合，33 对）** | **12.58 MB/帧** | **21.94 fps** | **+46%** |

- **`fuse_both` 是推荐调度**（`y1/reports/ddr_traffic_budget.md` §C0.3）。基线"逐层往返"31.94 MB/帧只能跑 8.64 fps，**过不了 10 fps** —— 所以**融合不是优化，是必需**。
- **当初计划的 `C6`（直连主口，绕开桥）已不需要**：现有桥在 `fuse_both` 下就已达到 15 fps 档且余量 +46%。
- **代价（待面积闸门确认）**：`fuse_both` 略掉的边界最大 **1.6 MB**，要求数据流支持**两种块序**的流式/行缓冲（不只是"逐层"）。这块缓冲的面积必须由面积闸门复核。
- **诚实边界**：275.9 MB/s 是**静态上限、非板端实测**；流量模型只计**激活流量**（不含权重装载、12 个头张量的后处理、突发对齐浪费）⇒ 是**下界**。故推荐调度刻意留大余量，不贴线。

### 2.2 算力与面积

| 项 | 推算值 | 备注 |
|---|---|---|
| 算力上限 | **18.6 fps** @100 MHz | 344.2 M-MAC ÷ 64 MAC/cycle |
| 实际 fps | 18.6 × **MAC 利用率** | 利用率由行缓冲深度决定（R2/R6）；**目标 ≥ 10 fps ⇒ 利用率 ≥ 54%** |
| DDR 激活带宽 | 见 §2.1（现约束 275.9 MB/s） | —— |
| APM（DSP） | **64** | 器件 740；现有 SoC 只用 4 |
| DRM（BRAM） | 权重常驻 ≈ **11** + 行缓冲若干 | 器件 415；现有 SoC 用 23.5 |
| LUT | 切片单独 **26,447 = 17%**（WIDTH=640） | 面积闸门 G1 已 PASS：`y1/reports/g1_area.md` |

## 4. 验收判据

**G1 面积闸门（先做，且必须有 —— M0 就是死在这一条）**
- NPU 单独 `dev_map`：**LUT ≤ 30,000、APM ≤ 100、DRM ≤ 60**；
- 并把结果加到本仓 SoC 基线（LUT 14,130.5 / FF 17,124 / APM 4 / DRM 23.5）上，断言 **SoC + NPU 全部 ≤ 器件可用量**（LUT 159,800 / FF 319,600 / APM 740 / DRM 415）。
- 判据脚本沿用 `check_dangling.py` + `check_no_xilinx.sh`，两者都要有正负对照。

**G2 卷积数值**
- 单元装置：一个 3×3 dense conv + 一个 depthwise conv，int8 量化后与 Python 参考**逐点一致**（允许 ±1 LSB，口径写死在装置里）。

**G3 分组卷积**
- `group = 4` 与 `group = 10` 各一个用例数值对（YuNet 里各 3 层）。

**G4 端到端数值（单帧）**
- 640×640 输入 → 12 个头张量，与 ONNX Runtime 参考在容差内一致。容差先在 1.0 里定死为「头张量逐元素 |Δ| ≤ 2（int8 量化后）」，若达不到则记录实测偏差并修订。

**G5 性能**
- 实测 ≥ **10 fps**（目标 15）。

## 5. 风险与开放问题

| # | 风险 / 开放问题 | 处置 |
|---|---|---|
| **R1** | **DDR 有效带宽从未实测**（本仓与 cam2lcd 只证了 DDR"能跑"，没测过有效带宽）。458 MB/s @15fps / 305 MB/s @10fps 是**全系统的绑定约束** —— 它比 MAC 数更可能决定成败 | **第一条实验就测它**（便宜、独立、结论决定后续）。测法：类似 `eth_bigframe_ab.py` 的两侧对照，主机发 + 板端读写大块并计数，得出有效 MB/s |
| R2 | 行缓冲深度 N 未标定：N 越深利用率越高、但面积越大 | 1.0 先冻结 N=3，Y2 用 `dev_map` 扫 N∈{2,3,5} 给面积/利用率曲线 |
| R3 | **"模型 → 指令 + 权重"的转换器要自写**（M0 已确认仓内没有） | Y3 单独成为一项；先只支持 YuNet 用到的算子（Conv 3×3/1×1、grouped、Relu、MaxPool、Resize、Add、Concat、Transpose/Reshape 落 CPU） |
| R4 | 前处理（letterbox 1280×720→640×640、RGB565→RGB888）放 CPU 还是硬件 | 1.0 先放 RV32（慢但简单），Y4 视帧率再考虑下沉 |
| R5 | 后处理（KPS/cls/obj 的 **Sigmoid**、anchor-free 解码、NMS）在 RV32 上够不够快 —— 12 个头、6400/1600/400 个先验框 | 1.0 先在 RV32 上实现并实测；若成为瓶颈再考虑硬件或换 CPU 侧算法 |
| R6 | MAC 利用率决定实际 fps；总线上 64 个 MAC 未必都喂得饱 | Y2 用单元装置实测利用率，而不是假设 |
| — | **开放**：是否做"不做 DDR 往返"的层融合/行缓冲版（省带宽、加面积） | 1.0 **不做**，留作 2.0 |
| — | **开放**：是否额外支持 320×320 档（带宽÷4、面积÷4） | 1.0 不做，但参数化时留好入口 |

## 6. 明确不做（1.0 边界）

- 不做视频流/多帧流水（先做**单帧**跑通）
- 不做立体视觉（双目只用 CAM0）
- 不做训练/量化感知训练（用现成 int8 量化工具产出的权重）
- 不做摄像头接入（Y5 再复用 `cam2lcd` 的行缓冲/DDR 路径）
- 不碰 LCD 显示

## 8. 证据等级声明

本 spec 中**所有** fps / 带宽 / APM / DRM 数字都是**由 YuNet 画像推算**的预算，不是实测；唯一实测过的硬件数字来自本仓与 `cam2lcd_200mini` 的既有日志（SoC 资源基线、相机 15.7 fps、DDR"能跑"）。**R1 与 G1 是这条线能否成立的两个关口。**
