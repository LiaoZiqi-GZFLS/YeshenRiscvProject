# spec：**NPU v2 —— 单骨架 + 可插拔算子核**（复用优先的重构）

- 日期：2026-10-16
- 触发：用户裁决「按推荐方法改进，**提升模块复用率**」
- 上游：`2026-10-14-y1-frame-runnable-design.md`（§3.1–3.7 的逐项缺口与补丁）、`2026-10-13-y1-runtime-width-and-tiling-design.md`（T-S0 钉死的 halo 规则）、
  `y1/reports/c4b_frame_runnable.md`（面积/回归账）、`y1/reports/ts3h_wide_chain_engine.md`（宽链 LUT 墙）

---

## 1. 一句话

把 NPU 从「**两套执行器骨架 + 三份 tile/取送实现 + 一串模式开关**」改成「**一个取送骨架（TileStreamer）+ 一组可插拔算子核**」，
在这条主线下同时解掉三问：**帧率**（打掉 23× 放大）、**资源**（删重复骨架，让链并发度有地方放）、**带宽**（请求形状改好）。

---

## 2. 复用率：先量化「现在有多不复用」（判据的锚）

| 功能 | 今天**几份** | 在哪 | 已有的税单（实测） |
|:--|:--|:--|:--|
| **行跨步窗口读 + 32 B band + per-plane idx** | **2 份** | `UnitExec` 宽路 gather；`BypassExec` tile 读 | **同一个缺陷修了两次**：T-S3b（`UnitExec`）与 T-S3e（`BypassExec`），两条侧向负对照、两个闸门 |
| **tile 网格 + halo + 掩码行写回** | **3 份** | 窄路 tile / 宽路 tile / 旁路 tile | 三个闸门各一套正负对照 |
| **执行器骨架（FSM + 缓冲 + 对账 + 主口互斥）** | **2 份** | `UnitExec`（含窄/宽两路）/ `BypassExec` | 行宽/几何对账的"钉子"每家一套（S1 改了两遍） |
| **计算核** | 5 个 | conv / maxpool / resize / add / sigmoid | ★ 这部分**本来就该分开** —— 复用不是把算子合并，是把**骨架**合并 |

**复用率的可证口径（三条，都要落成脚本或表）**
1. **骨架唯一**：全 RTL 里"行跨步窗口读 / 掩码写回 / tile 网格"**各只出现在一个模块内**（`grep` 可判，脚本化）。
2. **同一缺陷不再修两次**：per-plane band 的**两侧**负对照在**每一条使用路径**上都跑（一张"路径 × 负对照"表，全绿）。
3. **面积净下降**：删重复骨架后的 `dev_map` 净变化（LUT / DRM 记账）。

## 3. 目标架构：一个骨架 + 一组核

```
            ┌──────────────── TileStreamer（唯一取送骨架）────────────────┐
            │ 读  行跨步窗口 + 32 B band 对齐 + per-plane idx（唯一实现）  │
            │ 算  把列/行交给「算子核」（唯一接口：进 x、出 y + valid）      │
            │ 写  32 B 对齐 + wstrb 掩码行写回（唯一实现）                 │
            │ 网格 一个 tile 网格 + T-S0 已钉死的 halo 规则（唯一实现）     │
            └──────────────────────────────────────────────────────────────┘
                 ▲              ▲               ▲                ▲
            ConvCore       PoolCore       ResizeCore      AddCore / SigmoidCore
        （8×8 int8 MAC）  （2×2 max）      （2× 升采样）      （逐点 / 双源）
                 │
         ┌───────┴────────┐
         │ 趟编排 PassPlan │  窄层 = 1 趟；宽层 = ci/co 块多趟；链 = 多核串接
         └────────────────┘
```

- **窄层** = `ConvCore` 跑 **1 趟**；**宽层** = 同一个 `ConvCore` 跑 **多趟**（`C_in/GROUP` 分块）—— 不再是两套骨架。
- **链** = 多个核**串在同一个骨架上**（行锁步走 `FusionBuf`，中间张量零 DDR）—— 复用同一套读写与网格。
- **旁路** = **换核不换骨架**（maxpool/resize/add/sigmoid 只换计算核，取送/网格/写回全复用）。
- **一个 halo 规则**（T-S0 已逐字节证死），一个 tile 网格，一套 `rowW`。

## 4. 四件与复用正交、但互相加强的改动（= 我推荐的 B 档）

| # | 改动 | 治什么 | 量级（本项目实测锚点） |
|:--|:--|:--|:--|
| 1 | **窗口片上留住**（tile 的输入窗口跨趟复用） | 帧率（放大） | 宽路 tile 实测 **23.3×**（`c64_40x40`：102,400 B → 2,382,784 B）⇒ ÷`nCo` |
| 2 | **平面按 32 B 补齐**（转换器侧） | 帧率 + 资源 | `HW%32≠0`（20×20：`400%32=16`）逼出 per-plane band ⇒ 补齐后**整块可删** |
| 3 | **通道分块布局 NC8HW** | 带宽 + 资源 | 一"列"从 8 笔遥不相邻 32 B → **1 笔覆盖 4 列**（请求数 ÷4、突发连续）；per-plane band 结构性消失 |
| 4 | **两路合一**（窄/宽同一条路） | 资源 | LUT 墙：`Conv3x3Slice` **6,202 LUT/片**，L=8 ⇒ ~49.6k vs 余量 35,692 |

**为什么放一起**：分块布局（3）删掉 per-plane band 与一半 tile 分支（省 LUT）；补齐（2）删掉对齐分支（省 LUT）；省下的 LUT 让链并发度（4 的推论）有地方放；窗口留住（1）把放大打回去，帧率才回到融合模型的量级。

## 4.5 ★★ P0 实测结果（2026-10-16）—— **重心从"流量"挪到"调度"**

`y1/reports/npu_v2_accounting.md`（工具 `y1/tools/mac_account.py` + 闸门 `run_mac_account_ab.sh`；正对照**逐字节复现**冻结模型的两个已知值 `31.94` / `12.58` MB/帧）：

| 量 | 值 | 口径 |
|:--|--:|:--|
| 全帧**有用 MAC** | **344,224,000** | 逐层表（53 个 conv/dw 单元；taps 由 TYPE 导出） |
| **理想阵列上限** | **9.30 fps** | `MACs ÷ 64` @ 50 MHz（旧文档 18.6 fps 是误按 100 MHz 算的） |
| **实测调度（宽路 as-built）** | **1.11 fps**（带 tile halo 重喂 0.71） | 按 RTL 调度建模：每单元每像素每趟恒 9 个 tap-beat |
| v1 现状·带宽侧 | 6.52 fps（42.3 MB/帧，含实测 23.3× / 4.4×） | 模型（以实测放大标定） |
| 五档全做完·带宽侧 | 12.21 fps（22.6 MB/帧） | 模型 |

⇒ **① 带宽侧 21.9 fps 从未可达**；算力侧**即使 100% 理想也只 9.30 fps**。**目标帧率必须从算力账来定。**

⇒ **② 算力浪费被点名（以前没人算过）**：
- **1×1 卷积按 9 个抽头跑** ⇒ 那些层**烧 9×**（真表里大量 `t2` 型，且多在与 3×3 的融合链内）；
- **depthwise 对角趟只用 1/8 阵列** ⇒ 20 个 dw 层**烧 8×**；
- dense 整块 = **1×**（唯一不浪费的档）。

⇒ **③ 顺序修订**：**先修调度浪费（1×1 的抽头条数 / dw 的通道利用），再修流量**。流量五档全做完也只到 12.2 fps；调度修好是往 9.30 的上限走，且与流量叠加。

**⇒ ③b P0b 价签（2026-10-16 追加；账见 `reports/npu_v2_accounting.md` §P0b，闸门加正对照 D + 两条能发火的负对照）**：
45.08M issued 拍按类拆开 = **1×1 占 77.8%（浪费 9.49×）/ dw 占 17.8%（8.10×）/ dense 3×3 占 4.4%（2.88×）**——
单笔最大是 **`Conv_15` 一层 7.37M 拍（全帧 16.4%）**。价签（@50 MHz）：**A（1×1 只发 1 拍）−31.16M 拍 ⇒ 1.11 → 3.59 fps**；
**B（dw 用满阵列）−7.04M 拍 ⇒ 单做 1.31 fps；A+B ⇒ 7.27 fps**（残差 1.279× = 块内取整，第三项浪费）；理想 9.30。
**组合**：A+B + 流量 (e) 12.21 ⇒ **算力仍绑（7.27）**；但 A+B 单做、流量停在 v1 ⇒ 反而 **带宽绑（6.52）**——绑定侧会**翻面**。
**钟**：A+B 过 10 fps 需 `npu_clk` ≥68.8 MHz；理想式 ≥53.8 MHz（PnR 实测 54.14 **刚够**）。
**读法注**：A 的"跳拍"档（只留权重所在的槽 0 那一拍）数值逐字节不变、零布局改动；"中心拍"档拍数相同但动
blob+装载（可连带删 1×1 的 (+1,+1) 相位补偿）；B **不是纯调度**（共享 x 总线结构性分析见报告 §P0b-3，可行性=开口测量）。

**诚实标注（P0 自己列的）**：`275.9 MB/s` 是**静态桥路模型**（非持续实测）；(c) 32 B 补齐的**字节**收益 ≤1%（其价值在**资源**）；(d) 的"请求 ÷4"无法从现有锚点换算成 fps；(e) 单趟 Add 未实测；整帧**从未端到端跑过**。

### 4.6 由 P0 追加的两条设计改动（★ 价签 = P0b 实测，2026-10-16）

| # | 改动 | 治什么 | 量级 |
|:--|:--|:--|:--|
| 5 | **内层抽头条数按核尺寸走**（1×1 只跑 1 个 tap-beat） | 1×1 层的 9× 浪费 | 1×1 占真表 **26/53 单元、issued 的 77.8%**（9.49×）⇒ 单层最大 `Conv_15` 7.37M 拍（16.4%） |
| 6 | **depthwise 用满 8 条通道**（一条趟服务 8 个输出通道，而不是对角 1 条） | dw 的 8× 浪费 | 20 个 dw 层、issued 的 17.8%（8.10×）；`C_out∈{64,32,16,10,4}` ⇒ 8/4/2/2/1 趟，尾块照旧 |

**价签（P0b 实测，@`npu_clk`=50 MHz；base = as-built 45.08M 拍 / 1.11 fps）**：

- **改动 5 ⇒ −31.16M 拍（69.1% 总 issued）⇒ 1.11 → 3.59 fps**。两种落地读法**拍数相同**：
  ①"跳拍"（只留权重所在的槽 0 那一拍）**数值逐字节不变、零布局改动** [推荐先做]；
  ②"中心拍"（槽 4）需 blob 重生成 + 装载映射 + 可连带删 1×1 的 (+1,+1) 相位补偿。
- **改动 6 ⇒ −7.04M 拍（15.6%）⇒ 单做 1.31 fps；与 5 合并 ⇒ 7.27 fps**。
  ★ **前提警示**：8/64 槽有用是**共享 x 总线**的结构后果（`arrX(ci)=colWin(kx)(ci)(ky)`），
  一拍填满 64 个有用乘需要**数据通路改动**（每行 x 路由 / tap 向量化）⇒ 收益标 **modeled 上界**，
  保守界（2 拍/像素/趟）⇒ A+B 6.52 fps；**可行性 = 开口测量**。
  ★★ **B-1 已把这条开口测量做完**（见下方 §4.6a）：**上界不可达**（结构证明 + 实测），
  保守界 2 拍**就是可达界**；`A+B` 的**修正价签 = 6.52（2 拍档）/ 7.37（1 拍档）fps @50 MHz**，
  不是 7.27。
- **顺序**：5 的绝对收益是 6 的 **4.4×**（31.16M vs 7.04M 拍）⇒ **先 5 后 6**。
- 两条做完（A+B）残差 1.279× = **块内取整**（`Conv_0` ci 补位、`C≤4`/`C=10` 尾块）——**第三项浪费已在 §4.6b 报价**（切片 C-1）。
- 组合/钟：A+B + 流量 (e) 12.21 ⇒ 算力仍绑 7.27；A+B 单做 + v1 流量 ⇒ 带宽绑 6.52（翻面）；
  A+B 过 10 fps 需 ≥68.8 MHz、理想式 ≥53.8 MHz（PnR 实测 54.14 刚够）。

> ★ 改动 5（跳拍读法）**不新增功能，只改调度** ⇒ 与 §2 的"复用率"同向（删特殊档、统一内层节拍）。
> ★ 改动 6 经 P0b 复核**不是纯调度**（见上"前提警示"）⇒ 它其实是"阵列微结构"项：与 §3 的 ConvCore
> 接口一并改，落在 P4 段的判据里（否则 8× 的收益拿不到）。

### 4.6a ★★ **改动 6 的可行性测量与接口钉死**（切片 B-1，2026-10-16；交付物 = 独立探针，**零 RTL 改动**）

证据：`reports/npu_v2_accounting.md` §Slice B-1（探针 `rtl_test/DwLaneProbe.scala` + 装置 `rtl_test/DwLaneTb.v` +
闸门 `tools/run_dwlane_ab.sh`（绿）+ `tools/dw_lane_account.py`（四条锚）+ `pds/devmap_dwlane.tcl`）。

**① 结构结论（把"上界"钉死）**：阵列沿**列**做归约、行 = 独立累加器 ⇒ 一个 dw 输出值 = 9 个乘，
一拍最多吃 **8** 个归约项 ⇒ **每像素每趟 ≥ 2 拍**（64 槽里 72 个有用乘 = 56% 占用率，**结构性天花板**）。
P0b 的"理想式 1×"（992,138 拍）**不可达**；**保守界 2 拍就是可达界**。要低于 2 拍只能**加乘法器**。

**② 钉死的接口（四处，全部 additive / 行数中性）**
1. `Conv3x3Slice` +`dw_mode`（**只在 `TILING=true` 的展开里存在**，同 `one_x1` 的接线法）：dw 档像素相位
   `9 → 2` 拍（AFTER2）或 `1` 拍（AFTER1）；x 操作数从"8 宽广播"改成**逐 lane**
   `xLane(r,j) = Mux(dw_mode, colWin(j%3)(r)(j/3), arrX_dyn(j))`（**静态寄存器直连，零多路选择器**）。
2. `MacArray`：x 口逐 lane（或 additive `dw_x` 口 + 模式位）；AFTER1 档再加 `x8/w8`（第 9 抽头行）
   + `acc += sum + x8·w8`。
3. `WeightStore` +dw 对角读口 `dwTile(r)(j) = mem[r*8*9 + r*9 + j]`（+ `dwTile8`）；
   **blob / 装载器 / 描述符零改动**（现零填对角瓦片的 `(r,r)` entry 第 `j` 抽头就是"通道 r 的抽头 j"）。
4. `UnitExec`：`isDwW` → `mpu.io.dw_mode` 一行；装载器 / 趟循环 / 收料门 / `ps_clr` / `wide_passes` **全不动**。

**③ 实测价签（探针 dev_map，同器件同口径；Δ 是实测、摊到集成的读数是 modeled）**

| 档 | 拍/像素/趟 | ΔLUT | ΔAPM | ΔDRM | 摊到 1 个切片实例（推荐） | 摊到 9 个实例（最坏） |
|:--|--:|--:|--:|--:|:--|:--|
| AFTER2（无新乘法器） | 2 | +581 | +0 | 0 | 124,687 LUT / 542 APM | 129,335 / 542 |
| **AFTER1（+第 9 抽头行）** | **1** | **+317** | **+8** | 0 | **124,423 LUT（77.9%）/ 550 APM（74.3%）** | 126,959 / 614 |

**④ 修正后的 fps（@50 MHz；`beats` 是模型，dw 的 9/2/1 拍比是实测，四条锚全 PASS）**

| 臂 | beats | fps | 口径 |
|:--|--:|--:|:--|
| A（已落 RTL） | 13,920,400 | 3.5919 | 实计（Slice A） |
| **A + dw 2 拍（AFTER2）** | **7,673,600** | **6.5158** | modeled（实测拍比 × 真表几何） |
| **A + dw 1 拍（AFTER1）** | **6,781,200** | **7.3733** | 同上 |
| A+B1 + C（块内取整全修）地板 | 5,278,762 | 9.4719 | modeled 下界 |

**⑤ go / no-go 与判据规则**
- **推荐 go（AFTER1 档）**：规则 = **ΔLUT ≤ 1,000/实例 ∧ ΔAPM ≤ 8/实例 ∧ ΔDRM = 0 ∧ fps ≥ 10 在 A+B+C 且 `npu_clk` ≥ 53 MHz**。
  实测三条资源判据**全部满足**（+317 / +8 / 0）、PnR 实测可闭合 **54.14 MHz ≥ 53**。
- **AFTER2 是 no-go（相对目标）**：它把算力推到 6.5158 fps，**仍低于** v1 流量侧 6.52 ⇒ 花了 LUT 却**不翻面**
  （AFTER1 的 +8 APM 换来 13% fps 与"翻面到带宽绑"的余量）。
- **诚实边界**：`A+B` **单独在任何 ≤75 MHz 都到不了 10 fps**（A+B1 要 67.8 MHz；理想式要 53.8）；
  B1 的价值是"把 dw 的 8.1× 收到 1.0×（结构地板）"并把**绑定侧交给流量**，10 fps 仍要靠 **C + 钟**。
  未测：逐 lane x 选择器的**时序**（乘法器输入锥多一级）⇒ 实现片必须重跑 PnR；采集侧速率未测。

### 5.0 ★ 决策记录（2026-10-16，切片 A 验收后）

切片 A 已验收（**实测拍数比 9.00×、重算 3.5919 fps @50 MHz、回归 15/15、DRM 不变、LUT −2**），但暴露一条**关键耦合**：
**真表 26 个 1×1 单元全部是"链成员"**（19 head + 7 middle，**0 plain**）⇒ **A 的收益要等链路径才能兑现**。

**用户裁决：走"拆融合 + 窗口留住"**（而不是啃宽链引擎）。理由（信息已变）：
① 链编码**本来就与真表不一致**（B1 异型链 / B2 blob 段长漂移 19/19）；
② "忠实镜像"实测**撞 LUT**（+49.6k vs 余量 35.7k）；
③ A 的收益在**单点**路径上就能拿到，而宽单点路径**已逐字节验证**（T-S3a/b/d）；
④ 流量侧还有"窗口留住"这张牌没打。

**本路线的第一片（A2）**：**把宽 run 拆成 plain**（`y1_convert.py`；必要时按 A'-1 已钉的最小范围解冻 `desc_table.py`）。
- 窄链**保留**（它能跑且省流量）；只拆**宽** run。
- 随之而来：中间张量需要**真实 DDR 地址** ⇒ 张量分配器（arena）要扩；H1 的 `SRC_ADDR` 折进口径会简化（每个中间张量都有地址）。
- 判据：① 全部 67 单元的几何预检**零 err**；② 表相关闸门（`run_desc_ab` / `run_convert_ab`）重新锚定并全绿；
  ③ 冻结流量模型**重新发出**（拆融合的 MB/帧代价，用冻结工具**调用**而非改写）；④ **arena 装得进**预留区（`0x8040_0000–0x8200_0000`）；
  ⑤ 端到端：`npu_frame_run.py` 的表处理随之更新且自检通过。

### 4.6b ★★ **改动 4（C）的残差报价与接口钉死**（切片 C-1，2026-10-16；交付物 = 逐层价签工具 + 独立探针，**零 RTL 改动**）

**② 钉死的接口（DCI = "ci 进拍、tap 进 lane"；只 `TILING=true`，同 `one_x1`/`dw_mode` 接线法）**：

★★ **一处正确性补丁（实测发现，非可选）**：`MacArray` 的第 9 抽头积 `p8 = x8·w8` 是组合进 B 级，

  三网表逐字节冻结、**重跑 PnR**（c3 的 4:1 读在乘法器输入锥上）。
