### 10.2 根因 A（软件）：`/etc/inittab` 的 getty 把 tty 波特率改成 9600

- buildroot 默认那行是 `console::respawn:/sbin/getty -L  console 0 vt100`。
- busybox getty 对 speed `0` 的处理**不是"别动"**：`busybox-1.37.0/loginutils/getty.c` 原文
  `/* note: arg "0" turns into speed B0 */`，且 `if (speed != B0) cfsetspeed(&G.tty_attrs, speed);`
  ⇒ speed=0 **跳过 `cfsetspeed`** ⇒ `tcsetattr` 把 termios 里那份速度写回硬件，而内核给 tty 的
  初始 termios 是 **`tty_std_termios`**（`c_cflag = B9600 | CS8 | CREAD | HUPCL | CLOCAL`）
  ⇒ **端口被改成 9600**，与 `console=ttyS0,115200` 分叉。**"登录永远不成功"就是它。**
- 修法：本工程自带 `sw/buildroot-external/boards/naxmini/linux/rootfs_overlay/etc/inittab`，
  `ttyS0::respawn:/sbin/getty -L ttyS0 115200 vt100`（非 0 ⇒ `cfsetspeed` 生效）。
- **四者必须同档**：DTS `bootargs console=` ＋ serial 节点 `current-speed` ＋ OpenSBI `NAX_CONSOLE_BAUD`
  ＋ inittab 的 getty 参数。本轮统一回 **115200**（这档连 OpenSBI/earlycon 也验证过是干净的）。

### 10.3 根因 B（RTL）：`UARTRx` 丢背靠背字节

- `src/peripheral/UART.scala`：起始位采样后**只隔 3 个 baudTick** 就采第一个数据位（应 4 = 一位）
  ⇒ 全部数据位早半位；且 8N1 也**恒走 `sParity` 槽** ⇒ 停止位采样点晚 3/4 位，正好落进
  **下一字节的起始位** ⇒ 判帧错 ⇒ 整字节丢弃。**"打不进字"就是它。**
- 修法：`sStart` 校验通过后 `sampleCount := 1.U`；给 `UARTTx`/`UARTRx` 加 `parityEn`，
  8N1 时跳过校验位槽（`Uart16550` 恒接 `false.B` —— 它本来就只做 8N1；`UARTController` 接 `PARITY_EN`）。
- 顺带修掉一条**被掩盖的 TX 缺陷**：`UARTTx` 原来不管 LCR 怎么写都恒发一个校验位 ⇒ 一帧 11 位；
  对端按 8N1 收时"停止位"位置读到的是校验位 —— 校验位=0 的字节（`'H'=0x48`、`0x00`、`0x55`…）
  被判帧错。USB 桥一般仍交出字节 ⇒ **启动日志"看起来是对的"**，所以藏了很久。

| ③ 溢出 20 字节只吐前 16 个且 `OE=1` | OK |
| ④ 读一次 LSR 后 `OE` 清 | OK |

## 14. Phase 6 第二轮：**把 PHY/RGMII/引脚整层排除**（m6，2026-10-07 傍晚）

### 14.1 这一轮加了什么

只读观测窗从 4 字扩到 6 字（**仍在已路由的 `0xF000B0xx` 里 ⇒ 胶合不用改**）：

- `W4 = {txBytes, rxBytes}` —— GMII 上**发出/收到**的字节数（`tx_en`/`rx_dv` 有效拍数；GMII 1 字节/拍）
- `W5 = {rxRunMax, txRunMax}` —— **最长连续** `dv/en` 长度（判"是不是一个永不结束的帧"）
- 新增 `scripts/eth_dbg_read.py`：读 W0..W5 解码成人话 + **两轮差分**（哪些计数在动一目了然）

### 14.2 板上读数（m6）

| 计数 | 空闲基线 | 主机灌 60 个 ping 后 | 说明 |
|---|---|---|---|
| `rxcLo`/`rxcHi` | 1 / 1 | 1 / 1 | 时钟在跳（第二路互证 = 目视 led3 常亮）|
| `txBytes` | **65535（饱和）** | 65535（饱和） | MAC **从配置起就在狂流 `tx_en`**（与驱动无关），run ≥255 |
| `rxBytes` | 16189 | **16477（+288）** | **PHY 把主机帧送进 FPGA** ✓ |
| `txRunMax` / `rxRunMax` | 255 / 255（饱和）| 同 | 两向都出现过 ≥255 字节的连续 `dv/en` |
| MAC 内部 `rxCnt`/`writer_slot`/`CRC_ERRORS` | 0 / 0 / 0 | 同 | 收到字节**不存帧、连 CRC 错误都不记** |

### 14.3 结论（本轮把范围又缩了一大截）

1. **PHY + RGMII + 引脚这一层是好的**：主机帧进得来（`rxBytes` 随灌包增长）、`tx_en` 也真的在动。
2. **病灶在 LiteEth MAC 内部**：RX 侧**收字节但不存帧**（`writer_slot=0`、零 CRC/preamble 错误
   ⇒ 根本没走到校验那一步）；TX 侧**从配置起就流个不停**（`txBytes` 饱和、run≥255）；
   驱动握手 `READER_READY(0x1C)` 永不完成 ⇒ 后续发送全被拒。
3. ⇒ **不是引脚/时钟/DTS/驱动的问题**（这些都已逐条验过并排除）。

### 14.4 待查（下次接续）

- **LiteEth 生成参数 vs LiteX 惯例**：`tx/rx_cdc_depth=2048`、`with_sys_datapath=True` 下的 reset 处理、
  `nrxslots/ntxslots=2` 与驱动的 `litex,tx-slots` 是否一致；`tx_en` **从配置起就流**说明 MAC 的
  TX 数据通路一上电就认为"有帧在飞"（更像 CDC/指针初值或 reset 相关问题）。
- **子问题**：`rxRunMax` 饱和到 255，而单个 ARP 帧只有 54 字节 ⇒ `rx_dv` 可能跨帧一直高，待查。

## 15. Phase 6 第三轮：**真根因 = PHY 域复位同步器自锁**（2026-10-07 晚，m7）

### 15.1 怎么定位到的（承接 §14）

§14 已把 **PHY/RGMII/引脚整层排除**（时钟在跳、主机帧进得来、`tx_en` 也在动），只剩"**本工程自定义的两处**"：
`LiteEthPHYGMIIExt`（对 LiteEth 原版的裁剪）与 wrap 的时钟/reset 接法。于是**去读 LiteEth 原版**：

- `liteeth/phy/gmii.py` 的 `LiteEthPHYGMIICRG`：原版用
  `AsyncResetSynchronizer(cd_eth_rx/tx, reset)`（LiteX 的 `Special`，要平台原语，Pango 上没有 ⇒ 我们当初自写等价物）
  ⇒ **我们自写的那个等价物漏了"同步链必须 reset-less"**。

### 15.2 机理（读生成产物一眼看穿）

`third_party/liteeth_mac/liteeth_mac_top.v`（**修复前**）：

```verilog
reg [1:0] resetsync0_sr = 2'd0;
assign resetsync0_reset_out = (sys_rst_1 | (~(resetsync0_sr[0] & resetsync0_sr[1])));
always @(posedge eth_rx_clk) begin
    resetsync0_sr <= {resetsync0_sr[0], (~sys_rst_1)};
    if (eth_rx_rst) begin ... resetsync0_sr <= 2'd0; ... end   // ★ 复位时把自己清零
end
```

`eth_rx_rst = resetsync0_reset_out` ⇒ **链没满就复位、复位又把链清零 ⇒ 永远填不满 ⇒ `eth_rx`/`eth_tx`
两个 PHY 域被永久复位**。而 `pads_tx_en`/`pads_tx_data` 在 LiteEth 里是 `reset_less`（不受域复位影响）
⇒ 这正是"**线还在动、但 MAC 数据通路全死**"的全部现象来源。

### 15.3 修法（一行）

`sim/liteeth_gen/gen_liteeth.py` 的 `ResetSync`：`sr = Signal(2, reset=0)` → **`reset_less=True`**
⇒ 复制产物里 `if (eth_rx_rst) resetsync0_sr <= 2'd0;` **消失**（已验证），链在 2 个 eth 时钟后填满、复位释放。
（复位同步器的标准写法：初值由 FPGA 配置保证为 0，不参与域复位。）

### 15.4 生成环境的两条硬约束（都已踩，务必记住）

   用 **3.14 的 `litex_venv`** 会报 `Cannot extract clock domain name from code` / `Cannot extract CSR name from code`
   —— migen/LiteX 的 tracer 在新 Python 上失效。
2. 顺手把 `ClockDomain()` 写成 `ClockDomain("eth_rx")`（显式给名）更稳。
3. ⚠️ **本仓此前从未跑过这个生成器** —— 黑盒是从 `NaxYeshenLinux` **复制**来的 ⇒ 两边用的是**同一个坏产物**，

### 17.0 先撤回上一轮的两条结论（测试拓扑错了）

§16.2/§16.3 的"**TX 稳定 / RX 只有零星通过**"**作废**。两个错都在我这侧：

1. **网口认错**：板子实际接在主机 **ifIndex 5（`以太网`，192.168.1.105/24）**，不是 ifIndex 27。

   板子还从 ARP 里学到了主机 MAC。⇒ **RX 本来就是通的**，之前是激励发错了口。
   （判定法：`Get-NetAdapter` 逐个口的 `ReceivedBroadcastPackets` 增量，只有收数的那口才是链路；
   ifIndex 5 在修前 `ReceivedBytes` 累计 **0** —— 因为板子在修前一个帧都发不出，见下。）
2. **主机 ARP 缓存被代答**：`10.16.147.211 -> 00-00-5E-00-01-01`，而板子真 MAC 是
   DTS 固定的 **`02:00:00:00:00:01`**。更狠的是那段网有设备**替任意地址答 ARP**
   （新加的独有 IP `10.16.199.9` 也被同一个 MAC 认领）⇒ 单播测试到不了板子。
   ⇒ **别再用 `10.16.*` 那一段做判据**；本工程的验收口是 `192.168.1.110` ↔ `192.168.1.105`。

### 17.1 真根因（有板上证据 + 仿真复现）

`sim/liteeth_gen/gen_liteeth.py` 原来生成的是 **`dw=8` + `with_sys_datapath=True`**。

- `with_sys_datapath=True` ⇒ sys 域数据通路 **1 字节/拍**；sys = `soc_clk` = 100MHz ⇒ **生产 100 MB/s**。
- 而 GMII PHY 侧是 **8bit @ 125MHz = 125 MB/s**。
- `sys→eth_tx` 的 CDC 是 `source_valid = asyncfifo_readable` ⇒ **一帧中途 FIFO 就饿空**，
  `pads_tx_en` 被打成 **≤5 拍的小碎块** ⇒ PHY 看到的是 runt ⇒ **主机 NIC 全丢**。

**决定性证据（同一个观测窗里的不对称）**：

| 量 | 修前 | 修后 |
|---|---|---|
| `txRunMax`（最长连续 tx_en 拍数） | **4** | **101** |
| `rxRunMax`（最长连续 rx_dv 拍数） | 203 | 203 |

4 正好 = 100:125 的 **4:5**。RX 是"快生产→慢消费"，FIFO 只填不空 ⇒ 天然正常；
TX 是"慢生产→快消费" ⇒ 必然饿空。**这就解释了"RX 能用、TX 一个包不发"的全部症状。**

**依据（LiteEth 自己的生成器口径）**：`liteeth/gen.py` 里
`with_sys_datapath = data_width in [16, 32]` —— 官方**只在 16/32 位数据宽度**下开 sys_datapath；
`dw=8 + with_sys_datapath=True` 是**该库不会产出**的组合。LiteX 的 SoC 也正是 `dw=32` 跑主线驱动。

### 17.2 修法（三处）

| 位置 | 改动 |
|---|---|
| `gen_liteeth.py` | `dw=8 → 32`；`endianness="big" → "little"` |
| `third_party/liteeth_mac/liteeth_mac_top.v` | **重新生成**（Python 3.9 venv，见 §15.4） |
| `board/liteeth_wrap.v` | 槽口 **8bit 字节寻址 → 32bit 字寻址 + `wstrb` 作字节使能**（更简单） |

- `dw=32` ⇒ sys 域 4 字节/拍 = **400 MB/s ≫ 125 MB/s** ⇒ FIFO 只填不空。
- `endianness` **必须 little**：`dw=8` 时它是个 no-op，`dw=32` 取 `"big"` 会让**每组 4 字节组内反序**
  （读槽器 `reverse_bytes`），而驱动是 `memcpy_fromio/toio` 按**字节偏移**走的 ⇒ 必须字节自然。
  推导链：`wishbone.SRAM` 的 `sel[i] → 内存 lane i`（小端）+ 下行转换器（32→8）**先发 `data[7:0]`**。
- **DTS / 驱动契约不变**：槽跨距仍是 0x800 字节、rx 在前 tx 在后 ⇒ `litex,slot-size` 等不用改。

### 18.6 ssh 验收

- 端口探测：`192.168.1.110:22` OPEN，banner = **`SSH-2.0-dropbear_2026.93`**。
- **登录成功**（口令 `yeshen`）：返回 `uid=0(root)`、`uname -r` = `5.10.1`。

⚠️⚠️ **两条踩过的坑（不是链路问题）**：

1. **必须压低 KEX**。现代 OpenSSH 双方会协商到 **`sntrup761x25519`（抗量子）**，

### 18.7 ⚠️ 保留：ssh **不稳**（根因是已知的突发丢包，不是 ssh 本身）

- 旁证：三次 ssh 会话期间客户端 `TcpRetransSegs` **+62**（⚠️ 这是 WSL 全局计数器，

### 19.2 第一次上板：只解决了一半

- 驱动实测报 **`slots: tx 2 rx 4 size 2048`** ✓（RTL+DT 都对，不是"没生效"）。
- **50 帧背靠背 UDP：rx_packets 从 +2 变 +4**（等比 ⇒ 槽数确实是"在飞缓冲容量"的一部分）。
- **ssh 只从 1/4 变到 5/6，且多次贴 30 s 超时** ⇒ 主要问题没解决。

### 19.3 决定性实验（先验激励，再读源码）

1. **激励非零**：主机 `SentUnicastPackets` delta = **50**（5300 B = 50×106）⇒ 50 帧真的发出去了。
2. **板内**：`eth0` 中断只 **+13**、`rx_packets` 只 **+4** ⇒ 板侧丢，且"中断数 ≪ 帧数"。
3. 读驱动源码（`sw/buildroot-external/patches/linux/0002-…patch` 的 `liteeth_interrupt`）：
   ```c
   reg = read(WRITER_EV_PENDING);
   if (reg) { liteeth_rx(netdev); write(WRITER_EV_PENDING, reg); }   // ← 一次中断只搬一帧
   ```
   而 MAC 的 `WRITER_EV_PENDING` 是 **sticky**：突发里第 2 帧之后的事件**被合并进同一个 pending 位**
   ⇒ 中断次数远少于帧数、每次只搬走一帧。**对照组**：带间隔发 20 帧 ⇒ 20/20 全收（每帧各有一次中断）。

### 19.4 修法（软件侧，不动 FPGA）：按 pending 位循环排干

```c
int i;                                   /* ⚠️ 本内核按 C89 编，不能 for (int i…) */
...
for (i = 0; i < 128; i++) {              /* 上界只是防呆 */
        reg = litex_read8(priv->base + LITEETH_WRITER_EV_PENDING);
        if (!reg) break;
        liteeth_rx(netdev);              /* 先读 SLOT/LENGTH */
        litex_write8(priv->base + LITEETH_WRITER_EV_PENDING, reg);  /* 再清位=pop stat_fifo */
}
```
两个坑（都踩了并修好，写进坑清单）：
1. **改 unified diff 必须同步 hunk 计数** —— 第一版脚本把 `@@ -0,0 +1,N @@` 写成了 `@@ -0,N @@`（丢 `,0 +1`），
   已修回并逐 hunk 复核"头计数 == 实测 `+` 行数"。
2. **内核按 C89 编** —— `for (int i…)` 报 `only allowed in C99 or C11 mode` ⇒ `int i;` 提到函数头。

**证据**：`litex_liteeth.o` 编译通过；构建树内核源码 `grep -c "for (i = 0; i < 128"` = **1**；
新 `Image` md5 `d519b56bae855a749956ea738ef1cb23`。

### 19.5 第二次上板：ssh 收口

| 判据 | 修驱动前（m9+rx4） | 修驱动后 | 判读 |
|---|---|---|---|
| **ssh 成功率** | 5/6（3 次贴 30 s 超时） | **6/6** | ✓ |
| **ssh 单次耗时** | 5–30 s | **2–6 s** | ✓ 明显变快 |
| `ping` 回归 | 4/4 | 4/4（ifIndex5 收 +296 B） | ✓ 未退 |
| 50 帧线速突发 | 中断 +13 / rx **+4** | 中断 +10 / rx **+4** | 未变 |
| 启动 | — | `#2 SMP Wed Oct 7 23:40:49`、`slots: tx 2 **rx 4**`、`Starting dropbear sshd: OK`、`VEXIIYESHEN-OK` | ✓ |

### 19.6 结论：**两个杠杆各司其职**（别再混为一谈）

- **驱动排干循环 = ssh 的真杠杆**：ISR 把已缓冲的帧全搬干 ⇒ TCP 这种"略 paced + 会重传"的流量
  丢包大幅减少 ⇒ 握手从十几秒变 2–6 秒。
- **线速突发的上限 = MAC 的"在飞缓冲容量"（= 槽数）**，与 ISR 每次搬几帧无关 ⇒ 所以 rx 槽 2→4
  让极端突发从 +2 到 +4（等比），而排干循环对它是**中性**的。
- ⇒ 要彻底解决线速突发得换**更大的 RX 缓冲设计**（如 DMA 环）——**参数调不出来**：
  外设窗只有 64 KB，而一个 2 KB 槽的 32 个就吃满了。

### 19.7 本轮新增/踩坑（都写进 memory 索引）

- ⚠️ **换卡必断电/重烧**：FPGA 配置走 JTAG 是**易失**的 —— 断电换卡后串口**连 SDR 行都没有**（≠ 卡没接好）。
- ⚠️ **卡没插实**的判据（本轮又踩一次）：`SDR` 帧 `hex[2:10]` 的 **bit31 = misoHi = 0** ⇒ 没人在驱动 MISO。
  实测帧 `103A90001100000000`（`state=1, errCode=0, misoHi=0`）⇒ 重插即可，**别怀疑镜像**。
- ⚠️ **板内命令要短**：长命令行偶发坏字节（实测 `statistics` 被写成 `statistiistics`）⇒ shell 落进 PS2 续行、
  后续全乱。判据命令一律压到一行短命令（如 `grep eth0 /proc/net/dev`）。

## 20. 第 21 轮：**"让网口与 UART 稳定"——① 定位 ② NAPI(失败已回退) ③ 控制台修复**（2026-10-08 凌晨）

### 20.1 ① UART：**RX 是稳的；静默的真因是 `IXON` 软件流控**（零 RTL 改动就定了案）

**判别器是现成的**：8250 驱动把 `tty->icount` 暴露在 `/proc/tty/driver/serial`，
`fe`(framing)/`oe`(overrun)/`pe`(parity) **只在非零时才打印** —— 三类机理一次分开。

- **RX 风暴实测**：主机**满速**灌 **88 KB**（40×200 + 200×400 两轮）⇒
  `rx +88,689`（与发送量逐字节对得上，含 guest_cmd 自身命令行开销）、**`oe/fe/pe` 全 +0**
  ⇒ **RX 稳，别动波特/FIFO/RTL**。（`oe:1` 是更早遗留的孤例。）
- **控制台静默**（本轮又复现一次：登录前、`^Q` 前全静默）：
  - 硬件侧铁证：`IER=0x05`、`IIR=0xC1`（无中断待处理）、**`LSR=0x60`（THRE=1, TEMT=1 ⇒ 发送器空）**
    ⇒ **硬件空闲，问题在内核侧"故意不发"**。
  - 机理：内核 `tty_std_termios` 默认 `c_iflag = ICRNL | IXON` ⇒ 控制台 tty 吃 ^S/^Q；
    RX 流里出现**一个杂散 0x13(^S)** ⇒ tty **停发**（输出队列满 ⇒ shell/getty 阻塞在 write
    ⇒ 不读输入 ⇒ 什么都不回显），直到收到 **^Q**。
  - **A/B 正反双向**（`scripts/uart_xoff_ab.py`）：关 `-ixon` 后灌 5 个 ^S ⇒ 控制台照常；
    开 `-ixon` 后灌 1 个 ^S ⇒ **静默**、补 ^Q ⇒ 立刻回提示符。
- 杂散 `^S` 的来源嫌疑：**主机开串口时拨 DTR/RTS，CP2102 可能吐一个字节**（工具侧已在开口后补 ^Q）。

### 20.2 ② 网口 NAPI：**尝试 → 把板子挂死 → 干净回退**（留档，别再走这条）

- 动机：ISR 里"按 pending 位循环搬"仍受"一次中断只叫醒一次"的限；NAPI 轮询能抗中断合并/延迟并省中断。
- **结果：上板挂死**。症状：启动停在 `IRQDBG start`（探针没跑完、无 `VEXIIYESHEN-OK`）、**ping 3/3 全丢**、
  控制台静默且 **`^Q` 救不回**（⇒ 不是流控，是 CPU 侧）。
- **机理**：`liteeth_poll` 用 `WRITER_LENGTH != 0` 判空；而 NAPI 的语义是
  **poll 返回 `budget` = "还有活" ⇒ 立刻重进** ⇒ 判空条件一旦恒真就是 **softirq 风暴**，把 CPU 吃光。
  （LiteEth 的 stat_fifo 空时 `WRITER_LENGTH` **未必读回 0**。）
- **处置**：`git checkout` 回退到 §19 的"排干循环"版（坏版留档 `sim/reglogs/patch_napi_broken_bak.diff`）。
  **反向佐证**：回退后 `Image` 从 6,079,588 回到 **6,079,580** ⇒ 那 8 字节正是 NAPI 代码，回退确实生效。
- **结论**：网口不要碰 NAPI —— §19 的排干循环已达标（ssh 6/6 @2–6s），NAPI 在有 bug 时是**致命**的。

### 20.3 ③ 控制台修复（落地并上板验收）

## 21. 复核：「板 → 主机大帧 TX 坏」**未复现**（2026-10-08，m9）

### 21.1 缘起

工作区里出现一条**不是本记录作者写的**结论（写在 `docs/开发板功能清单-2026-10-08.md` 里）：

> 「板 → 主机发大帧（> ~1 KB）目前是坏的：小交互全通，**板发大报文或批量输出会整体卡死**」，
> 并据此推断 sntrup761 KEX 卡住的真因是"握手报文 >1 KB 撞上它"（判据形如 `1000 B ✓ / 1400 B → 0 B`）。

按纪律**先复核再入库**（不熟悉的改动不动、结论要能翻红）。

### 21.2 实验设计：**两侧独立观测的 A/B**

| 观测侧 | 量 | 为什么 |
|---|---|---|
| 板内（串口，独立于网络） | `/proc/net/dev` 的 eth0 `tx_packets/tx_bytes`（**驱动级 64bit**） | 不受网口本身影响；**不饱和** |
| 主机（ifIndex5 = 板子对口网卡） | `ReceivedBytes / ReceivedUnicastPackets` 增量 | 独立于板子自述：**帧到底有没有到** |

三臂（ICMP 载荷 S ⇒ 帧长 ≈ S+42）：`-c 3 -s 1000`（小帧正控）、`-c 3 -s 1400`、`-c 100 -i 0.02 -s 1400`（批量）。
脚本：`scripts/eth_bigframe_ab.py`。

### 21.3 数据（m9 + 现卡，2026-10-08）

| 臂 | 板内 `tx_packets/tx_bytes` | 主机 `bytes / unicast` | 判读 |
|---|---|---|---|
| 单发·小帧（3×1042 B） | **+4 / +3168** | +2144 / **+3** | 发出去了 |
| 单发·大帧（3×1442 B） | **+3 / +4326** | **+2884 = 2×1442** / +2 | 发出去了 |
| **批量·大帧（100×1442 B ≈ 144 KB）** | **+101 / +144242** | +132724 / **+93** | **发出去了** |

⇒ **板子单发与连发大帧都成功**（连发 144 KB、主机收到 93 帧且 `132724/93 ≈ 1427 B` = **整长未截断**）
⇒ **那条"大帧发不出去"的结论未复现**（§19 的 `dw=32` 修复本来就把 TX 通路做通了）。

### 21.4 那条误判从哪来（一个**新的仪器失效类型**）

第一次跑本实验时脚本读的是 **GMII 观测窗**（`0xF000B010/0xB014`）：`txBytes=0xFFFF`、
`txRunMax=0xFF` ⇒ 增量恒为 **+0**，**差点被我当成"没发出去"**。

⇒ **观测窗计数器是 16bit/8bit，早已打满**（它只适合"刚上电的头几十 KB"）——
**饱和计数器**是继"过滤/截断/恒绿"之后的**第三类"判据自己坏了"**；
本工程的判据此后一律用 **`/proc/net/dev`（64bit）+ 主机侧计数两侧独立**。

### 21.5 连带修正：sntrup761 卡住的机理

原记录把它归给"大帧 TX"，本记录前一版归给"RV32 算 PQ 慢"——**两条都不对**：

- 卡住点是客户端停在 `expecting SSH2_MSG_KEX_ECDH_REPLY`，且**此时板子 CPU 是 idle 的**
  （`loadavg 0.12`、`top` 无进程吃 CPU）⇒ **板子既没在算、也没在发**，是**客户端在等服务端的下一条报文**。
- 结合 §21.3（大帧 TX 通），⇒ 指向 **dropbear ↔ 新版 OpenSSH 的 PQ-KEX 互操作**问题。
  **结论不变且更强**：`-o KexAlgorithms=curve25519-sha256` 不是"绕开算力"，是**绕开一个互操作缺陷**。

### 21.6 顺带记的数据点（不下结论）

批量臂 **93/100**（1442 B × 100、间隔 20 ms）⇒ **7% 丢**。与 §17.6 的"2 槽在飞缓冲"口径不同
（那组是线速背靠背；这组是 20 ms 间隔仍丢 7%）⇒ 先记一笔，**要下结论得先做间隔扫描**
（间隔 vs 丢失率），别急。另：小帧臂 3 帧只记到 2 帧的字节（`+2144`），也与这处零星丢包同源。
